Frontend Guide: Multiple Check-ins / Check-outs

API
GET /api/v1/visits/{requestId}
Authorization: Bearer <token>

Use response.movementHistory.data for entry/exit history, NOT the existing summary timeline.

UI Rules

Pair each check-in with its checkout using departureEventId → 
event.id - Domain Premium Dijual / For Sale . Do not pair by array position.

Display occurredAt in movementHistory.timezone. API timestamps are UTC.

Use 
event.id - Domain Premium Dijual / For Sale  as the row key. Events already arrive oldest first.

departureEventId: null → show “No checkout recorded”, NOT “Currently inside”.

administrative_completion → show “Visit closed administratively” separately. It is NOT a physical checkout.

Keep unmatched checkout events visible; do not invent a check-in.

Empty data: [] → show “No movement history recorded”.

actor and gate can be null.

timestampBasis: "legacy_audit_time" → label the time “Legacy recorded time”.

Example UI in Asia/Riyadh:
Entry 1: Check-in 10:00 AM | Check-out 11:00 AM
Entry 2: Check-in 12:00 PM | No checkout recorded

Refresh
After a check-in or checkout, refetch the detail API.

To refresh only movement history:
GET /api/v1/visits/{requestId}/movement-history

This endpoint returns { requestId, timezone, data } directly.
