==================================================
TIME FIELD SEMANTICS
==================================================

Use these semantics consistently:

1. visitDate
   - Format: YYYY-MM-DD
   - Represents a business calendar date.
   - It is not an absolute timestamp.
   - Never parse it with `new Date(visitDate)` for comparisons.

2. visitTime
   - Usually HH:mm or HH:mm:ss.
   - Represents a wall-clock label in the visit timezone.
   - It is not an absolute timestamp.

3. visitStartAt
   - Canonical absolute instant.
   - ISO-8601 timestamp, normally UTC with a trailing Z.
   - Use this for countdowns, sorting, expiry, and upcoming-visit comparisons.

4. timezone
   - IANA timezone, for example `Asia/Riyadh`.
   - Use it when formatting visit dates and timeline timestamps.
   - If missing or invalid, fall back to `Asia/Riyadh`, never device local time.

5. Timeline, lifecycle, notification, check-in, and check-out timestamps
   - Absolute ISO-8601 timestamps.
   - Format these using the visit/business timezone.

6. scheduledEndTime
   - Wall-clock HH:mm value.
   - Do not convert it as an absolute instant.

Example:

A visit scheduled for:

    2026-07-30 10:00 Asia/Riyadh

is returned as:

    visitDate: "2026-07-30"
    visitTime: "10:00"
    timezone: "Asia/Riyadh"
    visitStartAt: "2026-07-30T07:00:00.000Z"

A device in Pakistan and a device in Saudi Arabia must compare the same
visitStartAt instant. Both should display the scheduled Saudi business time as
10:00 when the visit timezone is Asia/Riyadh.

- VisitListItemDto:
  - add `timezone: string`
  - retain `visitStartAt?: string`

  - ensure it has both `visitStartAt?: string` and `timezone: string`

  - add `visitStartAt`
  - add `upcomingVisitReminderMinutes`
  - support `type: "upcoming_visit"` and `action: "view_request"`

Make new fields optional where legacy records or older deployed backend
versions require compatibility.

2. Fix API response mappings

Ensure API mappers do not discard the new fields.

In particular, security visit mappings must preserve:

    visitStartAt: source.visitStartAt
    timezone: source.timezone ?? "Asia/Riyadh"

Reception detail/legacy visitor mappings must preserve the visit timezone from
visit details rather than silently dropping it.

Also check valet and buffet mappings and preserve visitStartAt when returned.

3. Make upcoming indicators ISO-only

Update the upcoming-visit timer/indicator logic.

Current incorrect behavior:
- It can reconstruct a Date from visitDate + visitTime.
- That parsing uses the device timezone.

Required behavior:

    const start = Date.parse(visitStartAt);

- If visitStartAt is missing or Date.parse returns NaN, return false.
- Do not fall back to parsing visitDate + visitTime.
- Compare `Date.now()` with visitStartAt.
- Keep the current visual threshold behavior unless explicitly required
  otherwise.

The visual upcoming icon currently uses a fixed 15-minute threshold. Keep that
for this minimum change because the runtime reminder-rule endpoint is restricted
to building administrators. Do not add a failing admin API call for normal
users.

The backend notification itself uses the configured threshold.

4. Remove duplicate client-side reminder generation

Delete or disable the local polling/toast hook that independently scans visits
and generates “upcoming visit” reminders.

Remove its usage from screens including:

- Employee/VisitorRequestsScreen
- Receptionist/AllVisitorsToday
- Security/SecurityCheckIn

Keep the existing push notification listener and persistent notification flow.
There should be one authoritative notification source: the backend.

Do not remove unrelated visit refreshing or list polling.

5. Fix push deduplication

When calculating the push notification deduplication key, prefer:

    messageId
    notification_id
    visitId
    requestId

Only use a generated fallback if none of these identifiers exists.

Do not use Date.now() before checking requestId, because it prevents duplicate
push events for the same visit from being recognized.

Parse upcomingVisitReminderMinutes defensively:

    const minutes = Number(data.upcomingVisitReminderMinutes);

Only use it when Number.isFinite(minutes).

6. Introduce central business-time helpers

In the existing date/time utility module, introduce or update helpers such as:

    const DEFAULT_BUSINESS_TIMEZONE = "Asia/Riyadh";

    formatAbsoluteTimestamp(
      isoTimestamp,
      options?,
      timezone = DEFAULT_BUSINESS_TIMEZONE
    )

    getBusinessDateKey(
      value = new Date(),
      timezone = DEFAULT_BUSINESS_TIMEZONE
    ): string

    isTodayInTimezone(
      isoTimestamp,
      timezone = DEFAULT_BUSINESS_TIMEZONE
    ): boolean

    isYesterdayInTimezone(
      isoTimestamp,
      timezone = DEFAULT_BUSINESS_TIMEZONE
    ): boolean

Requirements:
- Validate timezone identifiers.
- Invalid/missing timezone falls back to Asia/Riyadh.
- Do not fall back to the device timezone.
- Return date keys in YYYY-MM-DD format.
- Gracefully handle invalid timestamps.

Do not implement isToday/isYesterday using `Date.prototype.toDateString()`,
because that uses the device timezone.

7. Fix timeline rendering

Update RequestTimeline to accept:

    timezone?: string

Default it to:

    Asia/Riyadh

Format every absolute timeline timestamp using that timezone.

Pass the visit timezone into RequestTimeline from:

- Employee Request Details
- Manager Approval Detail
- Reception Visitor Detail
- Any other timeline caller found during implementation

Do not apply timezone conversion to visitDate, visitTime, duration, or other
wall-clock labels.

8. Fix reception actual-time rendering

Replace device-local formatting such as:

    new Date(value).toLocaleTimeString(...)

with the shared absolute timestamp formatter using:

    visitor.timezone ?? "Asia/Riyadh"

Apply this to checkedInAt, checkedOutAt, createdAt, or other absolute
timestamps shown on reception screens.

Do not convert scheduledEndTime because it is already an HH:mm wall-clock
value.

9. Replace device-local “today” calculations

Replace production usages of:

    new Date().toISOString().split("T")[0]

when the result means “today in the business” with:

    getBusinessDateKey(new Date(), "Asia/Riyadh")

Review at least:

- securityApiService
- requestMappers fallback date logic
- ReceptionistDashboard
- WalkInVisitors
- AllVisitorsToday
- receptionistVisitorState
- visitorRequestState
- valetAdminState
- buildingAdminState

Do not blindly replace code used to serialize a date explicitly selected by
the user. User-selected calendar dates should remain date-only YYYY-MM-DD
values.

10. Harden visit forms

Date/time pickers represent Saudi business wall-clock values.

For validation such as:
- selected date is today
- selected same-day time is in the past
- minimum selectable time

compare against the current Asia/Riyadh wall-clock time, not the device-local
wall clock.

Do not send ISO timestamps instead of visitDate/visitTime unless the existing
API request contract explicitly requires it.

The backend remains responsible for converting visitDate + visitTime in the
building timezone into visitStartAt.
