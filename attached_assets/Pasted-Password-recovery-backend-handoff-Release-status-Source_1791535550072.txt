Password recovery backend handoff
Release status
Source implementation exists; it is not activated, migrated or published. Recovery fails safely with HTTP 503 until enabled with valid configuration. No real mailbox delivery, production-password update or live SQL race was tested. The separate frontend/native application's QA remains an external release gate.

API contracts
Public endpoints under /api/v1/auth:

Endpoint	Input	Success
POST forgot-password	email, optional locale en/ar	202 {success:true,message:"If an eligible account exists, password reset instructions will be sent.",data:{accepted:true}}
POST reset-password/validate	opaque token	200 {success:true,data:{valid:true,expiresAt:"<actual UTC expiry>"}}
POST reset-password	token, newPassword, confirmPassword	200 {success:true,message:"Password updated. Sign in with your new password.",data:{reset:true}}
The existing transform adds a timestamp. No session, access/refresh token, profile or cookie is returned. Validation does not consume, extend or rotate a token. Unknown/inactive/SSO request addresses produce the same acceptance response and queue work without a synchronous account lookup. Worker sends only to active app-created users with an existing local password and no Azure identity.

Errors use {success:false,error:{code,message}} plus optional safe details:

400 RESET_LINK_INVALID for invalid, expired, consumed, replaced or ineligible.
422 PASSWORD_POLICY_FAILED with details.fields.newPassword for mismatch/policy.
422 INVALID_INPUT for email/language or malformed JSON.
413 INVALID_INPUT for recovery JSON bodies exceeding 8 KiB.
429 RATE_LIMITED with actual Retry-After seconds and safe retryAfter details.
503 RECOVERY_UNAVAILABLE for missing configuration or infrastructure failure.
Recovery responses are no-store. CORS exposes Retry-After and retains existing configured-origin settings; configure explicit approved origins before rollout. Do not broaden CORS or send cookies for public recovery requests.

Required frontend policy coordination
The backend keeps the eight-character minimum, rejects blank-only values and exact confirmation mismatches, preserves spaces, and rejects passwords exceeding 72 UTF-8 bytes (bcrypt's input limit). Apply the same guidance to recovery and signed-in Change Password; do not trim submitted passwords. The provided frontend's six-character assumption must change before release.

Legacy client compatibility change
Old send/verify/resend OTP, reset-with-OTP and legacy password-reset JWT service paths now return HTTP 410 RECOVERY_LINK_REQUIRED. They were not secure delivered recovery and must not bypass the new eligibility, single-use or session rules. Update any clients still using them to the three email-link endpoints. Previously issued password-reset JWTs are not accepted as opaque reset tokens. Local login, Microsoft login/callback, invitations and roles are not replaced.

Persistence and activation
The additive migration creates reset hashes, encrypted durable mail jobs, revocation epochs and shared rate buckets. It has not been run.

Before activation, approve and apply the migration using the external SQL Server backup/schema-verification procedure. Do not assume the workspace's migration history matches the server. The migration intentionally refuses destructive down migration: deleting revocation epochs would revive older access tokens.

Configure each environment through secure settings:

RECOVERY_ENABLED=true only after schema/configuration and QA approval.
RECOVERY_FRONTEND_ORIGIN: explicit approved HTTPS frontend origin, no path, query, fragment, embedded credentials or development-preview domain. QA links must point to QA, production links to the production frontend.
RECOVERY_MAIL_KEY: a dedicated base64-encoded 32-byte encryption key stored as a Secret, never in source, chat or a public environment variable.
Existing SMTP configuration must be valid; no new email provider is introduced.
Authentication storage contains only hashes. Durable outbox content is AES-256-GCM encrypted; a pending job can contain an encrypted token so retry uses the same link. Protect the key independently from SQL backups. Do not rotate it while pending jobs exist without a reviewed drain/re-encryption procedure.

Session behavior
Successful reset consumes outstanding tokens, updates bcrypt password, increments the account's revocation epoch, revokes refresh tokens and deactivates biometric registrations in the same transaction, then queues a credential-free notification.

Access JWTs include recoveryVersion. The existing JWT guard checks the current epoch in SQL. Pre-migration/legacy tokens count as version zero; once that user's epoch advances they are rejected. Pausing recovery does not disable these checks or restore sessions. Missing migration is supported before rollout; database verification failure rejects authentication rather than silently accepting a JWT.

Token issuance/refresh is serialized on the account lock and rechecks current password/status plus refresh revocation, preventing a stale login/refresh racing reset from issuing a new valid session. Already-running authorized requests are not forcibly interrupted. Users may sign in normally with the new password and register biometric credentials again through existing authorized flows.

Mail, retries and operations
The worker runs every 15 seconds, claims at most ten jobs per pass, uses 180-second leases and at most five delivery attempts with 120-second retry delays. Dead workers' expired leases are reclaimable. Retries reuse the encrypted token, do not mint new ones, and discard links no longer valid/eligible. Replacement issuance invalidates older tokens; older queued requests cannot supersede a newer issuance or issue a link after a subsequent reset.

SQL enforces the 15-minute token expiry with UTC server time. Emails show the actual UTC expiry so retry delay is not misrepresented as a fresh 15 minutes. Fragment links are used: /reset-password?lang=en#token=<opaque token> or ar. Plain text and escaped HTML/RTL copies contain no passwords or invented contacts.

Requests are bounded by 30 per IP and 8 per address/token subject per 120 seconds, shared across the three endpoints, plus account-bound valid-link limits. Request rate counters commit independently of failed token/password validation. Queued jobs are capped at 10,000. Completed jobs wipe payloads; terminal jobs and expired tokens/rate records have bounded retention. SQL worker logs are generic and include no reset payloads. Ensure operational alert collection monitors recovery worker/queue failure warnings and stranded/failed job counts.

Recovery and OTP application logs omit URL queries. Sensitive email sending suppresses provider error details. Infrastructure owners must separately verify reverse-proxy/APM request-body/header logging, SMTP tracing and email-provider link rewriting/tracking settings; application code cannot certify those systems. Do not run link tracking that strips fragments or records full reset URLs.

QA evidence and remaining release checks
Verified in this workspace: 55 targeted recovery/admin-guard tests passed, TypeScript build checking passed, application restart succeeded, and Swagger rendered. Live development requests to all three public endpoints returned 503 RECOVERY_UNAVAILABLE with no-store while disabled; an oversized body returned 413 with no-store. A read-only SQL query confirmed pre-migration epoch-zero compatibility. No migration or credential write was performed by that check.

Before rollout, verify trusted-proxy/IP handling: limiting uses Express req.ip, not a blindly trusted client-supplied forwarded header. A shared proxy address will conservatively share an IP bucket until trusted-proxy handling is configured and validated for the actual hosting topology.

Offline fixtures cover neutral acceptance, eligibility changes, opaque encrypted tokens, validation/replay, one-success concurrent redemption, policy errors, queue retry/expired links, rate/error contracts, legacy-route retirement and revocation while recovery is paused. Fixture transactions are serialized in memory: they are not proof of real SQL Server isolation or race behavior.

Before calling recovery working:

Approve an isolated QA migration and test account/mailbox only.
Exercise real concurrent issuance/redemption/refresh/login and worker-crash lease recovery on SQL Server, including rollback and SMTP failures.
Receive actual en/ar mail, verify fragment/privacy and correct QA destination.
Confirm old password fails, new password succeeds, and old refresh/access/ biometric credentials fail while an unrelated account stays signed in.
Check CORS Retry-After from a real browser and verify frontend responses, cooldowns, expiry, RTL/accessibility and native cold/warm-link behavior.
Regression-check local/SSO login, signed-in Change Password, invitations and role routing in the deployed QA client.
Inspect logs/provider tracking using synthetic tokens; never publish real reset secrets or test passwords as evidence.
