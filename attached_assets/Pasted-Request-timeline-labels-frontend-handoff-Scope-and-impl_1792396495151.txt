Request timeline labels: frontend handoff
Scope and implementation boundary
Implements the four supplied cases:

No recorded visitor attendance, followed by administrative closure.
A non-parking visit with multiple successful check-in/checkout cycles.
A visitor checked in without checking out, followed by 9 PM daily-cutoff completion.
A visitor accepted but never arrived, followed by administrative completion.
The confirmed visible wording for both no-attendance cases (1 and 4) is No-show, not Admin closure or Visit Completed. This supersedes the earlier case 1 recommendation to display Admin closure.

The backend source now supplies simplified movement labels and additive presentation rules. The actual timeline frontend is maintained outside this repository; these instructions must be applied there before the screenshots change.

This is presentation-only. Stored status, timestamps, event types, movement boundaries, event pairing, QR expiry, re-entry eligibility, notifications, resources, and administrative closure processing remain unchanged. No database migration is required.

API locations
GET /api/v1/visits/:id: use movementHistory.presentation and movementHistory.data.
GET /api/v1/visits/:id/movement-history: the same object directly, with presentation, data, requestId, timezone, and qrValidity.
These are additive fields in the existing history envelope, not a new endpoint. Existing authorization remains in force.

Frontend requirements:

Display presentation.statusLabelOverride when non-null in the detail's visible status, instead of mapping completed to “Visit Completed”.
Keep the stored status: "completed" for existing workflow logic. Do not change status filters, permissions, actions, or API mutation payloads.
When hideVisitCompleted is true, omit the separately generated “Visit Completed” timeline step.
Hide administrative rows and their descriptions using hiddenEventIds. Render finalTimelineEvent once as No-show, using its occurredAt and stable sourceEventId. The underlying administrative event stays unchanged.
Honor hideUnrecordedSteps: omit unfulfilled check-in/checkout placeholders. Determine fulfillment from recorded evidence, not icon color.
Keep actual submission/approval/acceptance and other recorded events. Do not hide genuine rejection or cancellation events merely because they are not green.
Do not show the Admin closure explanation for these hidden rows. Do not manufacture arrival or departure timestamps.
Expected screenshot timeline:

Request Submitted
Auto-approved
Visit Approved
No-show
The No-show override requires completed status, a recorded administrative-completion event, no recorded physical movement (including parking or an orphan checkout), and no legacy checkedInAt or checkedOutAt. This describes absent recorded attendance, not proof that the person never physically arrived. Missing history alone is not enough to infer a no-show or administrative closure.

Other attendance/closure cases retain their existing completion display unless explicitly covered below. In particular, this does not relabel every completed visit as an administrative closure.

Render returned events in order, keyed by stable event ID, excluding only IDs in presentation.hiddenEventIds (case 3 below). Keep the full response unchanged. Format occurredAt using the response timezone; keep all cycle timestamps.

The administrative event remains in data for audit and now includes completionReason: "daily_cutoff". Only its ID is marked hidden for display; do not delete it from the response, persisted history, or audit views.

Use timeline.completedAt for the completion timestamp, formatted in the response timezone. The actual daily cutoff is 21:00 Asia/Riyadh (18:00 UTC for these examples). Never replace that time with the browser clock or the event's ingestion/recordedAt time. If legacy detail lacks a completion timestamp, the identified cutoff event's occurredAt is completion evidence, not checkout evidence.

The rule requires completed status, a recorded daily-cutoff reason, and an open building check-in with no recorded departure or current checkout timestamp. An earlier completed entry/exit cycle does not prevent this case if a later building re-entry remains open. Keep all earlier real checkout rows. Legacy checkedInAt can establish check-in when movement rows are absent.

Do not classify the case solely because a displayed time happens to say 9 PM. No-show daily closures still follow case 1. Parking-only presence, ordinary scheduled-end completion, a later recorded physical checkout, and non-completed current statuses do not trigger case 3's hiding rule.

Important: “Visit Completed” here means the request was closed at the daily cutoff. It does not prove physical departure. checkedOutAt/Actual OUT remain null unless a real checkout was recorded; presence, security, and QR-policy logic must not infer checkout from the completion row.

Case 4: visitor accepted but did not arrive
Acceptance is not attendance. Once this request closes administratively without recorded movement, it uses the same No-show rules as case 1:

Request Submitted
Auto-approved
Visit Approved
Visitor Accepted — only if a real acceptance timestamp exists
No-show — original closure occurrence time (2:00 PM in the supplied screenshot)
Do not show Check In/Checkout placeholders, Admin closure or its explanation, or Visit Completed. Preserve the actual acceptance timestamp; do not replace it with the closure time. status remains completed and the audit event remains administrative_completion. No-show is a presentation label, not a new API status or a new stored event.

The original administrative event is hidden via hiddenEventIds; its replacement is described by finalTimelineEvent. Render exactly one No-show row. If multiple administrative records exist, the final row references the last chronological closure, while all underlying audit records remain intact. Use its occurrence timestamp, not acceptance time, scheduled end guessed by the client, or the browser clock.

A request still awaiting arrival with current status visitor_accepted is not automatically a No-show. The existing completed/closure-evidence checks remain mandatory. No attendance is inferred from acceptance, and no physical movement is inferred from No-show.

Integration outline
const history = detail.movementHistory;
const rules = history?.presentation;
// Display only. Continue using detail.status for existing workflow decisions.
const visibleStatus =
  rules?.statusLabelOverride ?? existingStatusLabel(detail.status);
const hiddenEffects = new Set(rules?.hiddenQrEffects ?? []);
const hiddenEventIds = new Set(rules?.hiddenEventIds ?? []);
const movementRows = (history?.data ?? [])
  .filter(event => !hiddenEventIds.has(event.id))
  .map(event => ({
  key: event.id,
  label: event.displayLabel,
  timestamp: event.occurredAt,
  helperNote: hiddenEffects.has(event.qrEffect)
    ? null
    : existingQrEffectText(event.qrEffect),
}));
const finalRow = rules?.finalTimelineEvent
  ? {
      key: rules.finalTimelineEvent.sourceEventId,
      label: rules.finalTimelineEvent.displayLabel,
      timestamp: rules.finalTimelineEvent.occurredAt,
      helperNote: null,
    }
  : null;
// In the existing timeline composer:
// 1. Keep recorded lifecycle events (submission, approvals, acceptance, etc.).
// 2. Use movementRows for physical cycles and visible administrative closures.
// 3. If rules.hideUnrecordedSteps, do not add unfulfilled placeholders.
// 4. If rules.hideVisitCompleted, do not add the synthetic Visit Completed row.
// 5. Avoid duplicating legacy check-in/out or closure rows already in history.
// 6. Case 3 keeps Visit Completed at timeline.completedAt; do not create checkout.
// 7. Render finalRow once, in chronological order with the other visible events.
//    Cases 1/4 show No-show instead of both Visit Completed and Admin closure.
This is illustrative integration code, not a replacement timeline component. Inspect the frontend's real response selectors and lifecycle event sources. Apply hidden IDs consistently if a separate lifecycle/event-log source also renders the same administrative event; do not reintroduce its row or description. Do not reconstruct all cycles from timeline.checkedInAt/checkedOutAt, the latest IN/OUT summary, array parity, or mutable status.

For list badges, these presentation rules are currently supplied by detail/history, not added to every list endpoint. Do not issue a history request per list row or guess a no-show from list status. A list-wide override needs a separately scoped batch contract if required.

Frontend acceptance checks
No-show administrative closure: visible status and final row “No-show”; no Admin closure row/text, empty check-in/checkout, or “Visit Completed” step.
Underlying status remains completed; original timestamps are unchanged.
Two entry/exit cycles: four rows with Check In/Checkout labels, original timestamps, and no Reception/Parking prefixes.
The three helper notes are hidden, including a checkout after meeting end.
QR validity, re-entry errors, polling, and mutation behavior are unchanged.
Recorded physical checkout keeps its row; absence of checkout never creates one.
A legacy arrival/checkout or parking arrival prevents the no-show override.
Missing history does not imply no-show. A stale closure does not override cancelled, auto-cancelled, checked-in, or accepted status.
Recorded non-green rejection/cancellation events remain visible.
Older backend responses without presentation remain readable; do not derive administrative closure from completed alone.
Checked in without checkout at daily cutoff: Check In followed by Visit Completed at 9 PM; no Admin closure row/text and no empty Checkout placeholder.
An earlier real checkout remains visible when a later unclosed re-entry triggers case 3. No fabricated checkout, departure linkage, or Actual OUT.
An actual checkout before or after cutoff, parking-only arrival, or a scheduled-end event at 9 PM does not trigger case 3's hidden-ID rule.
The hidden cutoff row remains in the API/audit history with its original timestamp and daily-cutoff reason.
Acceptance followed by no attendance: preserve recorded Visitor Accepted, then show one No-show row at closure time. Acceptance without completed closure evidence never produces No-show.
Multiple administrative audit rows produce one No-show replacement row, with no stored data changes or duplicate administrative rows on the UI.
